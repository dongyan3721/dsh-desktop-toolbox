## 1. 当前结论

三个分支可进入集成审查，尚不能视为可发布插件。已完成的真实能力是 **无桌面窗口的便笺存储桥**；图片仅交付工具适配层，原生转换方法尚未实现。

先交付便笺内部联调里程碑，再补齐图片转换，之后才达到原迁移计划中“便笺 + 图片”的 MVP 范围。此阶段不接入截图、剪贴板、使用统计、脚本和密码本，不使用真实用户数据。

## 3. 合并前需要处理的问题

| 优先级 | 事实或缺口 | 下一步处理 / 通过标准 |
| --- | --- | --- |
| P0 | Node 客户端发送 cancel 后立即移除 pending 并报告 CANCELLED/TIMEOUT；原生只承诺尚未开始写入时可取消。本轮未证明调用返回取消即表示原生停稳 | 定义调用等待结束、原生任务终态与已提交写入的区别；实现有限时的取消收敛/终态跟踪；用延迟写入夹具验证竞态，禁止据此盲目重试写操作 |
| P0 | 插件入口仍是 prototype 状态工具，没有原生进程所有权、ready 后注册、失败恢复与有序卸载 | Codex 补 Host 装配，确认实际宿主子进程策略；真实 Loader 验证启动、取消、失败、卸载和父进程退出，无残留进程/锁/工具 |
| P1 | 便笺工具允许 limit≤100、任意非负安全 offset；原生限制 limit≤20、offset≤10000 | 本轮采用较小的原生范围，工具描述/校验、协议及测试统一；同时对齐标题、正文、查询长度和大小单位 |
| P1 | Node FrameDecoder 的 Buffer.toString('utf8') 会替换非法字节；实测含 0xff 的 JSON 字符串未被拒绝 | 使用严格 UTF-8 解码；新增非法 UTF-8、分包字符边界测试，确保失败后连接与 pending 清理符合约定 |
| P1 | decoder 用 typeof object 判断载荷，实测接受 JSON 数组；ready 仅验证 capabilities 是数组，未验证每项为字符串；响应/事件检查不完整 | 拒绝数组信封；明确允许字段和值域；补 capabilities、result/error、event、未知 ID 和版本测试 |
| P1 | close() 的强制销毁定时器未在正常关闭时清理；已销毁 socket 路径是否等到真正 close 尚需核对 | 审查并补充异步清理测试；close 幂等且达到约定的停稳状态，关闭后无本客户端留下的 timer/signal/socket 资源 |
| MVP 阻断 | 原生 capabilities 没有 media.convert_image，现有媒体模块公共接口不能直接满足指定输出路径、拒绝覆盖和取消收敛 | 在原媒体模块提供最小公共适配，再接桥；通过真实格式转换与文件边界测试后才注册图片工具 |

P0/P1 是本项目本轮的实施优先级；问题并不意味着此前全部单元测试失效，而是已有测试尚未覆盖这些跨层契约。

还需重点审查原生队列/取消 ID 的资源上限、便笺更新与更新时间令牌的写入一致性、异常退出的数据锁释放。这里只列为审查项，未声称已经复现故障。Antigravity 交接中的基线 `caf643f` 与实际共同祖先 `3901564` 不一致，验收记录应以 Git 事实修正。

## 5. 集成顺序与门槛

### A. 契约修正与审查（估计 0.5–1 日）

固定上述交付 SHA，逐项审查并形成修正清单。先对齐分页/长度、终态与取消、帧与信封校验。给每个已确认反例加回归测试，修正后仍保留此前 70 项测试。

退出门槛：已确认问题修复，待验证项有对应测试结果或明确限制；禁止仅修改交接文档以宣称解决。

### B. 便笺三层正式联调（估计 0.5–1 日）

拟建立 `integration/notes-mvp` 分支和 `.worktrees/integration` 工作树，基于冻结版本引入三方提交及修正，不直接在 main 试合。无需重建三位工作树。

把本次诊断提升为正式测试，覆盖真实 native release + Node 客户端 + 工具工厂：

1. ready/capabilities，便笺创建→查询→更新→版本冲突。
2. 停机→同目录重启→查询同一条；同一数据目录的第二实例被拒绝。
3. 同时请求、未知方法、非法帧和协议不匹配。
4. 写入前/写入中/提交后的取消和超时，确认实际数据库状态、终态和重复请求策略。
5. 桥断开、父进程退出和关停，确认进程、锁及连接释放。

退出门槛：这些路径通过，且 fixture 数据仅在集成工作树中生成。此时可以称“便笺三层链路完成”，仍不等同于插件入口或完整 MVP 完成。

### C. 接入 Harness 插件生命周期（估计 1–2 日）

补齐 Config：可信原生二进制位置、数据目录、启动/调用/停机超时、支持模块、读写范围。配置默认值与错误在加载边界明确检查。

核对当前 Harness 子进程 Provider 的执行与所有权语义，由插件启动固定随包 exe；ready 后才开放能力。status 从真实连接和 capabilities 派生，不再固定写 prototype，也不把进程“已创建”当作“已 ready”。

只注册 bridge 实际提供的便笺方法；图片工具保持不注册。将停止新调用、处理在途工作、请求原生关停、等待退出、关闭连接和超时兜底放入一个有序的 effect 清理流程。不能在 disposer 中递归 dispose 自己的 Fiber。

退出门槛：真实 Cordis Loader/隔离 Profile 下可调用便笺；启动失败有明确原因；反复 20 次加载/卸载后无重复工具、进程或锁；手工 ctx.plugin 或 fake client 不替代此验收。

### D. 补齐图片转换（估计 1–2 日，可与 C 的独立部分并行）

给 mod-media-proc 增加可复用的受控图片转换入口，明确指定输出路径、无覆盖发布和取消检查点。按既定授权设计验证真实路径、父目录、junction/symlink 和输入输出范围；避免“先检查不存在，再直接覆盖写入”的竞态。

真实夹具至少覆盖 PNG/JPEG/WebP 等已宣称格式、坏输入、已存在输出、无权限/越界路径、取消及临时文件清理。核对产物格式、尺寸和实际文件内容。

退出门槛：原生 capabilities 包含经验证的 media.convert_image；授权回调、桥和原生端各自按职责落实；之后才在插件中注册图片工具。便笺与图片均通过才达到原计划 MVP 的功能范围。

### E. 发布候选与 main 合并（估计 0.5–1 日）

生成包含 Host JS、Patch、必要原生 exe/资源的预构建 tgz。发布 manifest 分别记录插件版本、协议版本、原生源码 SHA、宿主兼容版本和二进制哈希，不把原应用 0.1.3-beta 当成插件的版本号。

包中不包含开发 SDK、worktree、测试数据库、本机绝对路径或安装期编译脚本。固定宿主 peer，不打入第二份 Cordis。

在 D 盘干净 DSH_HOME 中安装 **生成的 tgz**，检查配置、实际启动、便笺/图片真实操作、重启、升级和卸载清理。验证运行不依赖原 C 盘项目、其他 agent 工作树或源码 TS loader。

退出门槛：集成分支全部验证通过，未测试限制写入说明；检查最后 diff 与产物清单，再合并 main，保留三位原分支和工作树供追溯。发布到 npm 或用户日常 Profile 不属于本轮计划动作。
